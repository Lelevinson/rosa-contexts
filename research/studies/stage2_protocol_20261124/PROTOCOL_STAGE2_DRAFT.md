## 1. Question, hypothesis, status of the claim
- **Question.** When the same typed, guarded action tool is given to every system, does method M (short menu, structured finish, errors as text, name fix) change how often turtlesim action tasks are completed correctly and truthfully, compared with E1x (strong ordinary baseline) and S0x (original ROSA)?
- **Hypothesis (a hypothesis, not a result).** M is not worse than E1x on supported-complete episodes. The development evidence for actions is **class B (no effect seen; 128 episodes, [report](../action_dev_switch_20261118/REPORT.md))**, so a null result is the expected outcome and will be reported as such.
- **What Stage 2 is for.** It checks that the guarded tool, the judge and the runner work on a pool nobody tuned against, and it measures the arms descriptively. **14 tasks give a wide interval; there is no significance claim.** Established method: typed tool with bounded arguments and a goal budget (engineering). Not claimed as novel.

## 2. Controls (same for every system)
- Identical typed action tool `rotate_to_heading` and pose read tool, from one deployment policy (field range [-pi, pi], goal budget 3, acknowledgement 2 s, execution deadline 15 s, cancel settlement 3 s), post-action state OFF. Unit-tested identical across XM, XS0, XE1.
- Systems: **XM** (M + tools), **XE1** (E1 + tools), **XS0** (stock ROSA, 47 tools + tools). F is excluded (no action adapter). Stock write paths stay blocked by the pilot guard; the typed tool is the only way to move the robot.
- Same models (lfm3:1.7b, qwen3.5:9b, gpt-oss:20b, bonsai-2:4b), temperature 0.7, same seeds, same master-seed shuffle, one GPU job at a time, Ollama pinned as in Stage 1 (rev 2 freeze), ROS domain separate from any running Stage 1 job.
- Fresh simulator per episode (new `turtlesim_node`), so no state carries over.

## 3. Cells (owner decision of 2026-11-24, after the timing run)
14 tasks x 3 systems x 4 models x seeds. **Lab: 3 seeds = 504 cells. Laptop: 3 seeds (504) if its run can start by about 18:00 on 2026-11-24, otherwise 2 seeds (336).** Both specs are pinned in one freeze; the laptop's choice is made at launch, recorded in the launch note and never changed afterwards. The 2-seed spec is a complete prefix of the 3-seed spec (same cells, same order; tested), so a 2-seed laptop run is the first two seeds of the same design. Measured basis: the timing run (36 public dev cells, laptop, mean 57 s per cell) projects 3.1 / 6.1 / 9.2 h for 1 / 2 / 3 seeds at laptop speed ([record](../exam_actions_20261121/TIMING_RECORD_laptop.json)); the live check with the real bridge on two public one-goal tasks took 8-19 s per warm cell, so held-out tasks with reads or longer chains are the main time uncertainty. Seeds, task shuffle and order follow the queue rules (complete pairs, seeds first). The lab and the laptop are separate strata, never pooled.

## 4. Measurements
- **Primary:** supported-complete = judge success (v1.2 + answer-form normalisation): independent final state within tolerance and still, the answer consistent with it, the ordered steps dispatched and completed in order, and for read-then-act tasks a successful read from the bound source **before** the dispatch. Tolerances and step contracts are the custodian's, frozen with the pool.
- **Truthfulness, counted separately:** `claimed_but_not_arrived` ([claim_counter.py](../exam_actions_20261121/claim_counter.py)): the structured answer reports the arrival field within tolerance of the target while the independent state is not. A 2x2 table (claimed/not x arrived/not) per system and model is reported. Free-text claims are not counted (limit).
- **Cost:** model requests, input and output tokens, native ROS operations, goals sent, pose reads.
- **Ending classes (one per episode):** supported, unsupported, no answer, iteration cap, backend error, timeout, validation abort, guard-blocked write attempt, **unresolved_motion** (class (b)), **unscored** (class (c)), **infrastructure** (class (a)).
- **Reported per model and pooled; per task descriptive only.**

## 5. Invalidation classes (from PROTOCOL_DRAFT section 3, implemented in the runner)
- **(a) before the first request:** fixture graph check fails (`/turtlesim` missing or a real extra node), simulator not ready, or start state not still/at heading 0 (+-0.05). Row = infrastructure; the queue re-runs the cell once; both attempts are logged.
- **(b) agent-caused unresolved motion** (executor ends LOCKED after an unknown goal, or the robot is still moving at the end, after at least one request): an agent outcome, never re-run, own ending class.
- **(c) after a request, the fixture check or the independent state read fails:** cannot be re-run, cannot be scored; ending `unscored`, kept in the denominator. Reported counted as failure and excluded. More than 3% of a system's cells stops the study for an owner decision. A system with more than 5% class (a) or (c) cells is flagged in every table; more than 10% overall makes the study compromised.
- **Fixture check design (lesson of Stage 1):** `graph_settle.check_fixture_graph` waits for transient `_ros2cli_*` helper nodes (a lingering ROS command from a tool call) to disappear, treats a listing that misses the simulator as a **discovery miss** (retried, never "clean"), ignores remaining CLI helper nodes but records them, and never ignores a real extra node. The row stores settled, waited seconds, discovery misses and ignored count for both checks. Tested with fakes (10 tests) and against a real turtlesim in domain 231.

## 6. Success reading (accepted by the owner 2026-11-24; reported descriptively, fixed before the run)
1. **Validity first:** class (a)+(c) below 5% per system and unscored at most 3%; no stray write by a stock tool; no lock-in failures attributable to the harness. If not met, the result is reported as compromised.
2. **Comparison M against E1x (and each against S0x):** supported-complete difference in percentage points with a 95% cluster bootstrap over tasks (same procedure and seed as the Stage 1 analysis script, so no new analysis code is needed for the point estimate), plus the token ratio. **Reading rule, descriptive only:** "no evidence of a loss" if the lower bound of the difference is above -5 points. With 14 tasks this will usually be wide; an inconclusive interval is reported as inconclusive.
3. Truthfulness: the claimed-but-not-arrived counts per system, no threshold.

## 7. What is not a protocol change, and what is
After the first held-out request nothing changes (tasks, tolerances, prompts, tools, judge, bridge). A needed change is a written, hashed revision reported separately with its own results. Failed and quarantined cells are reported, never dropped. The quarantine rule of [2026-11-23](../../decisions/2026-11-23-stage1-quarantined-cells.md) **applies to Stage 2 in the same way (owner decision 2026-11-24)**: paired exclusion is primary (a pair is task, model, seed; M against E1x), the worst case for M is the sensitivity, and skipped cells are reported per system x model x cause for each machine. The Stage 1 analysis revision ([analysis_rev3.py](../analysis_rev3_20261124/analysis_rev3.py)) implements it for the Stage 1 plan; Stage 2 needs the same run with its own spec and its extra ending classes, which has not been done.
