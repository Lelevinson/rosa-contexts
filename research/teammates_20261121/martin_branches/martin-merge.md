## Fit, rules and test gate

**Inference.** Merge-candidate for a separate Stage 2 development comparison, currently **BLOCKED / NOT YET JUSTIFIED** for implementation or a live benchmark. The parameterized form avoids fixed task answers and uses the same deployment rights as the matched control. Shared guard enforcement matters even on the no-motion path. A pre-read must not turn a malformed or out-of-range goal, an unresolved prior goal, or missing evidence into a success. Task-required reads must be visible to the judge with their real source and order. If the judge requires a dispatched goal for a step, a no-motion shortcut cannot satisfy that step under the existing rule. Establish the allowed semantics before freezing a new comparison. An internal pose read cannot stand in for a different required read, such as a parameter. (Our `research/studies/action_dev_switch_20261118/judge_v1_2.py:65–135` and `research/studies/exam_actions_20261121/tests/test_exam_actions.py:118`.) Stage 1's 18 dev questions need no action arm. A Stage 3 test needs new public Nav2 tasks plus a guarded navigation backend and separate approval.

**Verified from code and reported only for historical outcomes.** The closest closed studies are post-action state and report-gate sizing, which [the runtime review](martin.md#rules-and-fit-with-m) compares at code level. Our action report records 216 vs 203 requests and 54 vs 42 verification calls over 64 episodes per arm. The candidate adds a pre-read and can skip a goal. Our existing ON path already returns state on a goal-sending call, so using only OFF as a control could credit the bundle for an existing shortcut. The total verification counts do not tell us how many requests a bundle would remove. (Our `research/studies/action_dev_switch_20261118/run_action_study.py:117–120,143–189` and `REPORT.md:5–20`.)

**Inference.** A decision-changing first step, if separately authorized, is to inspect only the 8 dev action tasks' saved traces under a frozen rule. Count cases where a separate verification read used its own model request and the equivalent observation could have been provided by the action receipt. Count possible already-at-target skips only where the saved prerequisite state and requested target are both known. Keep those opportunities separate and record the denominator, extra native reads and any overlapping requests. The plan stops below a 10% ceiling on saved requests. A ceiling between 10% and the proposed 25% live bar still needs a distinct credible route to the live bar. Martin's UR5e results and the old pose-attachment comparison cannot resolve this. The closest ordinary control is the existing guarded action with post-action state enabled, which can already collapse a later model read.

**Inference.** If that gate clears, freeze three paired dev rows per task/seed/model: existing XM (receipt OFF, context), guarded XM with the existing receipt ON (decisive comparison), and M with the parameterized bundle under the same allowed goal range, budget and data access. Keep one action tool per menu, the same finish path, an independent judge, and scored step traces. Run a fake-transport check before any live test. Require zero guard/trace violations. Use the plan's proposed per-model signal rules against the decisive control: at most 1 fewer success out of 16 paired runs, at least 25% fewer requests on jointly successful pairs, at least 80% adoption when a rotation is needed, and at most 10% growth in tokens or native operations. Also report all-episode costs and failures. Stop for a guard violation, unreadable trace, or failure to meet the signal bar. These are proposed decision thresholds. They are not frozen or validated.
