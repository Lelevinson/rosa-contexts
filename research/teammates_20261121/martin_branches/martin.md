## Goal and mechanism

**Verified from code.** The goal is to let the model choose a permitted skill and let Python handle routine robot steps. At this tip:

- `MacroROSA.__init__` loads only the supplied tools and uses synchronous execution. `MacroROSA.invoke` adds the public skill catalogue as JSON to the request. `BoundedPromptROSA._get_prompts` replaces the known ROSA generic prefix and keeps the robot-specific messages. The prompt requires one tool call per response. `single_action` rejects a multi-call response before dispatch. The model sees five tools in both modes. `select_skill(skill_id: str)` selects once, `read_state(nodes: list[str])` reads, `write_state(node_name: str, values: dict[str, number])` requests a write, `verify_outcome()` acquires fresh evidence, and `submit_report(status, observation_id)` takes SUCCESS, FAILURE or UNKNOWN and a string ID. (Martin `src/rosa_reliability/macro_agent.py:97–120`, `prompt_contract.py:13–49,60–72`, `terminal.py:51–60`, `workflow.py:18–19,86–98,145–163`, `tools.py:10–24,66–79`, `reference.py:15–17,65–74`.)
- In primitives mode, selecting returns the target and the model manages the steps. In macro mode, `MacroSession.run_workflow` reads the current fields, stops the automatic sequence if values are unavailable, writes once if the known state is outside tolerance, and reads again for verification. Even if no write is needed, it verifies. It returns the observation or a failure reason and gives the next decision back to the model. The runtime neither reselects the skill nor automatically replays the command. (Martin `workflow.py:86–98,134–138`, `macro.py:15–41`.)
- `SkillRegistry.register` stores an ID and a fixed numeric target for one named node. A deployment provides the transport and can restrict the skills offered. `CapabilityRegistry` also accepts read-only inspection skills with a named subject, manually selected data sources and Boolean checks. Inspection reads those groups, represents true/false/unavailable as 1/0/null in numeric evidence, and refuses writes. The demo registers fixed UR5e home and offset poses. (Martin `bounded_macro.py:30–57,85–124`, `capabilities.py:19–45,54–93,105–162`, `ur5e_macro_demo.py:18–22`.)
- `_RegisteredSession.write` requires the exact registered coordinates and a known prerequisite observation. `ExecutionSession` checks budgets, sends at most one write in this workflow, and lets transport exceptions propagate so the macro stops without replay. The UR5e transport checks the complete six-joint target and a range around home, publishes a trajectory, and reads a newer joint-state sample for verification. The publication receipt itself only confirms a local request. `report_reference` checks that the cited observation is current and complete. `AcceptedReportExecutor._get_tool_return` ends on a trusted accepted report without another model acknowledgement. (Martin `bounded_macro.py:60–82`, `workflow.py:36–40`, `macro.py:39–41`, `execution.py:14–32,105–130,155–215`, `ros_arm.py:25–27,40–92`, `reference.py:32–62`, `terminal.py:30–48`.)
- The optional `ToolContractOllama` profile is separate from the skill logic. It forces non-streaming, adds a system message containing family guidance and a copy of the schemas, and rejects other families when tools are present. Its guidance table lists `llama3.1` and `granite3.3`. (Martin `src/rosa_backends/tool_contract_ollama.py:11–16,27–47`.)
